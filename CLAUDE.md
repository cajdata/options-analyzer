# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An options scanner. It pulls option chains from Alpaca, ranks contracts by visible rules, and sets each stock's earnings history beside what the options price in. It also types each stock's recent headlines and SEC filings by event and shows what followed earlier events of the same type. A positions page sets what the person already holds against the exit rules. Since phase 4 (started 2026-11-26) a paper view sends orders to Alpaca's paper account, and a journal records what the scan showed for each paper trade and how it ended.

It can send one kind of order: a limit order to the paper account, which holds pretend money, that the person has written out and confirmed. It has no way to send an order to a live account and must stay that way until phase 5 is asked for. Everything else only reads. It shows rules and numbers, and the person decides: nothing in it sends, cancels or closes anything on its own.

```powershell
.venv\Scripts\python.exe -m pip install -e ".[dev,ai]"                # install
.venv\Scripts\python.exe -m pytest -q                                  # all tests
.venv\Scripts\python.exe -m pytest tests/test_risk.py -q               # one file
.venv\Scripts\python.exe -m pytest tests/test_risk.py::test_the_spread_is_a_cost_to_both_sides -q
.venv\Scripts\python.exe -m app scan --demo                            # command line, synthetic data
.venv\Scripts\python.exe -m app serve --demo                           # dashboard at http://127.0.0.1:8000
.venv\Scripts\python.exe -m app pool                                   # widen the pool news events are compared across (live: about two minutes)
.venv\Scripts\python.exe -m app positions --demo                       # what is held, checked against the exit rules
.venv\Scripts\python.exe -m app paper --demo                           # the paper account, the journal, which signals worked
.venv\Scripts\python.exe -m app paper --demo open CRUX 2026-12-18 400 put --sell   # writes an order out; --send sends it
```

- `--demo` uses the synthetic provider and needs no keys. Without it the app needs Alpaca keys in `.env` (see `.env.example`).
- `positions add` and `positions remove` change the positions file (`data/positions.json`, or `POSITIONS_FILE`) and need no keys. That file is the person's own and is ignored by git: never write a made-up entry to it to try something out. Use `--demo`, or a `Settings(positions_file=...)` under a temporary folder as the tests do.
- `paper open`, `paper close` and `paper cancel` reach the paper account. Without `--demo` that is the person's real Alpaca paper account, and with `--send` an order goes to it. Never run one of those without `--demo` unless the person asked for that order: see the working agreement. `--demo` goes straight after `paper`, and its account and journal live in memory for that one run.
- The journal (`data/journal.json`, or `JOURNAL_FILE`) is the person's own, like the positions file, and git ignores it. Never write a made-up trade to it. Use `--demo`, or a `Journal` under a temporary folder as the tests do.
- No linter is configured. CI (`.github/workflows/tests.yml`) runs pytest on Python 3.11 and 3.13 for every pull request, so code must run on 3.11.
- `main` is protected on GitHub (since 2026-11-25): a merge needs both checks, "Python 3.11" and "Python 3.13", to have passed, for the owner too, and a push straight to `main` of a commit that has not passed them is refused. The rule names the checks by the workflow's job names. If the matrix or the job name in `tests.yml` changes, change the rule's required checks along with it, or every pull request will wait for a check that never reports. A branch does not have to be level with `main` to merge.
- `.claude/launch.json` defines two dashboards for the preview tools: `strike-check-demo` on port 8765 (synthetic data) and `strike-check-live` on port 8766 (needs the keys in `.env`). The server does not reload: restart it after changing Python code. A third entry, `strike-check-site` on port 8768, serves the landing page in `docs/` with the system `python`.
- With `ANTHROPIC_API_KEY` set, the live dashboard shows a "Write brief" button and `scan --brief` works. Each use is a billed call: ask before making one.

## Architecture

One scan flows in a straight line:

1. **Providers** (`app/providers/`) fetch data. `MarketData` is the protocol; `AlpacaData` is the real one and `DemoMarket` the synthetic one. `EarningsService` combines earnings sources (SEC EDGAR, Alpha Vantage), caches them on disk, and estimates a missing date. `NewsService` (`providers/news.py`) combines headlines (`AlpacaData.headlines`) with 8-K filings (`EdgarEarnings.filings`) and keeps both on disk.
2. **`Scanner`** (`app/scanner.py`) picks symbols (given ones, or discovery from the watchlist, screeners and `data/universe.txt`), then analyzes each on a small thread pool.
3. **Analysis** (`app/analysis/`) runs in a fixed order per symbol: `contracts` (per-contract metrics) → `earnings` (past reactions, implied move) → `risk.history_vol` (history-based volatility) → `scoring.score` → `risk.assess` (risk/reward). `scoring.rank` runs last, across all symbols. `exits.build` then draws an exit plan for each ranked contract, and `Scanner._add_news` loads news and runs `events.context` for each stock that has one. `Scanner._pool_studies` then adds those stocks to the pool (`app/pool.py`) and gives each its pooled studies.
4. **Surfaces** read the resulting `ScanResult`: `app/server.py` (FastAPI plus `public/index.html`), `app/__main__.py` (command line), `app/ai.py` (optional Claude write-up).

A review of positions is a second, shorter line through the same parts (`Scanner.review`). `positions.PositionStore` hands over what is on file. The held contracts are quoted by name (`MarketData.option_quotes`), and each stock held gets the earnings context a scan gives it (`Scanner._reports`, shared with `_analyze`). `exits.build` draws the path from the entry price, `analysis/holdings.py` sets the rules against each position, and `_add_news` adds the news. The server and the command line read the resulting `PositionsReview`. The AI brief does not.

Paper trading is a third line, and the only one that sends anything. `paper.PaperDesk` writes an order out as a `Ticket` (`write_open` from a contract in a `ScanResult`, `write_close` from a journal entry), and `send` takes a ticket's id and hands the order to `broker.AlpacaPaper`, or to `broker.DemoBroker` in the demo. `journal.Journal` keeps each `Trade`. `PaperDesk.review` reads the account's orders and positions, brings the journal up to date (`paper.reconcile`), sets what the account holds against the exit rules through `Scanner.review`, and sums up the closed trades (`analysis/signals.py`). The server, the page's Paper view and `python -m app paper` read the resulting `PaperReview`. The AI brief does not.

Things that are not obvious from any one file:

- **The lens decides late.** `contracts.analyze_contract` produces lens-independent metrics priced at the mid. Only afterwards, in `Scanner._analyze`, does the lens ("buy" or "sell") set `pop`, `outlay`, `score` and `risk_reward`. A `ContractAnalysis` is therefore filled in across several modules.
- **`history_vol` is the shared yardstick.** `risk.history_vol` blends ex-earnings realized volatility with past report-day variance. The score's volatility component and the risk/reward rating both start from it, which is why the rating is shown beside the score and never added into it.
- **Provider caveats travel as notes.** A provider appends to `market.notes`; the scanner drains them into `ScanResult.warnings`, which every surface displays. Use this for anything the person should know (a feed fallback, missing open interest).
- **Time is injected.** `Scanner(today=)`, `EarningsService(today=, clock=)`, `AlpacaData(now=, sleep=)` and `EdgarEarnings(sleep=)` exist so tests never depend on the wall clock. Tests pin `TODAY = date(2026, 11, 24)`. `--demo` and the demo dashboard are the exception: `build_scanner` starts their market from the wall clock, so `tests/test_scanner.py` holds it at `TODAY` with the `demo_day_is_pinned` fixture. Without it the command-line tests pass only on that one day. The demo's paper desk and its account take their day from that market (`paper.build_desk`, `paper._demo_clock`), so holding the market still holds them too.
- **Tunable numbers live in two places.** Score weights and thresholds are in `scoring.LENSES`; rating thresholds are constants at the top of `risk.py`.
- **Shared data types live in `app/models.py`**, including the exit-plan dataclasses, so they can be imported anywhere without a cycle. `exits.py` holds only the logic. Exit plans are kept in `ScanResult.exit_plans`, keyed by contract symbol, and not on `ContractAnalysis`.
- **Presets are data.** `scanner.PRESETS` maps a name to `ScanRequest` fields. The API serves it, the dashboard builds its buttons from it, and the command line reads it, so a preset is defined once.
- **The dashboard builds DOM with the `el()` helper.** Never use `innerHTML` with scan data.
- **News is typed late, like the lens.** A source returns raw `NewsItem`s. `events.classify` sets the event type afterwards, from two tables in `analysis/events.py`: `HEADLINE_RULES` (keywords, first match wins, so the order is part of the rule) and `FILING_ITEMS` (8-K item codes, most telling first). With the company's name to go by (`events.aliases`), a type also has to fit where the headline puts the company: see the invariants. Labels, the flagged types and the cautions are served by `/api/status`, so the dashboard holds no copy of them.
- **News lives on `UnderlyingContext`** (`news`, `news_elsewhere`, `recent_events`, `event_studies`, `coverage`, `pooled_studies`, `news_note`), filled in only for a stock with a ranked contract. `Scanner(news=None)` leaves it out.
- **A check on a position is worded once, in Python.** `PositionCheck.label` and `.detail` are made in `analysis/holdings.py`, so the page and the command line cannot word a rule two ways. The rules' titles reach the page through `/api/status`.
- **The dashboard has three views in the one file**, Scan, Positions and Paper. Each element belongs to a view through `data-view`, `show()` switches them, and the address ends in `#positions` for the second and `#paper` for the third. The notes under the controls are kept for each view (`notices`).
- **The page draws two lists of held positions with one function.** `BOOKS` names the table, the detail pane and the open row of each: what the person entered (Positions) and what the paper account holds (Paper). `renderHoldings` and `showHolding` take the review and the book, so a fix to one list is a fix to both.
- **The file handling for the positions and the journal is one class** (`store.ListFile`). `PositionStore` and `Journal` say what an entry means, and share how a file is read, written and refused.
- **`docs/` is the public site for strikecheck.app**, published by GitHub Pages from that folder on `main`. It is one plain HTML file with no scripts, plus `CNAME` and `.nojekyll`. Its sample table and earnings bars were copied from a `scan --demo` run and its claims come from the README, so change them together. Since 2026-11-27 it describes the positions page and paper trading as well as the scan. It still leaves out the whose-news rules and pooling. The dashboard itself is never hosted there: it has no login and runs on the owner's keys.

## Invariants

These came out of two rounds of outside code review. Each has a test; do not regress them.

- **Risk/reward is in present value, priced at the fill.** `risk.assess` uses the ask to buy and the bid to sell, and discounts the payoff. A fairly priced option must show zero edge at any expiry, and a buyer's "most you can lose" must equal the cost shown. (A seller's outlay is collateral, a different number: the most a short put can lose is the strike less the bid, and a short call has no cap on its own.) Display metrics on `ContractAnalysis` (breakeven, `pop`, annualized yield) stay at the mid.
- **A quote below exercise value is rejected**, using plain `max(S-K, 0)` or `max(K-S, 0)` whether or not the feed supplies a volatility. Do not swap in a discounted European floor: it drops legitimate deep in-the-money calls on dividend stocks. "Below" is below by more than `contracts.PRICE_TOLERANCE`: prices are amounts in cents and a float is not one (`100.0 - 80.10` is `19.900000000000006`), so without the room a price exactly at exercise value was rejected about one time in four.
- **Earnings math.** `TRADING_DAY = 1/252`; a report replaces one trading day. `risk.event_variance` uses log returns and takes `(sessions - 1)` ordinary days out of a two-session reaction. `earnings.spans` treats unknown timing as possibly before the open, and `earnings.implied_move` leaves a report-day expiry of unknown timing out of both sides (`_ambiguous`).
- **"No reports" and "cannot tell" are different.** A company that files 6-K, 20-F or 40-F raises `Unsupported` in `EdgarEarnings`, which sets `earnings_unknown`. Never let it look like an ETF, which has no reports at all.
- **The strike window scales with volatility** (`Scanner._strike_window`). A fixed 15% cuts off the deltas the sell lens targets on volatile stocks.
- **A file in the cache that does not read as an entry is a miss, never an error** (`DiskCache.entry`): the wrong shape, no value, a time with no zone. The same goes for what is inside it: reports that do not read as reports (`EarningsService._on_file`), a pool record whose counts disagree (`pool._counts`). One spoiled file used to stop every pooled study on a scan.
- **A short earnings history is not kept when a source could not be asked** (`EarningsService.history`). Three reports from the SEC with Alpha Vantage at its limit used to be stored for a month, long after the limit had passed. A source that cannot answer for the company at all (a foreign filer) is different: that answer is kept, or the other source would be asked on every scan.
- **One server instance runs for days.** `EarningsService.today` is read each time, never stored at startup. The calendar and the Alpha Vantage block expire and retry; that block is checked and set while holding its lock. `Scanner._lock` allows one scan at a time. `DiskCache.set` is atomic and never fatal. `EdgarEarnings` is paced (`MIN_INTERVAL`). `/` is served with `Cache-Control: no-cache`.
- **An exit plan is a standing-still path, and says so.** `exits.build` reprices a contract on later dates with the stock unchanged. The path starts at the quoted mid and is never below exercise value. Closing early uses the bid for a holder and the ask to buy back, so the spread is counted twice. An earnings report's variance leaves on `earnings.reaction_day`, and the last chance to close before it is `earnings.session_before` that day, never a weekend. A date on the path must never be shown as the chance of getting there, and the profit target and time stop (`exits.PROFIT_TARGET`, `exits.TIME_STOP_DTE`) are presented as rules of thumb.
- **The exit path counts time in calendar days, so the report takes one calendar day** (`exits.REPORT_SLOT`), not `TRADING_DAY`. With the longer trading-day slot, stepping past the report hands back half a day of ordinary time, and at one or two days to expiry the option came out priced higher after the report than before. The one-off decompositions in `risk.py` and `earnings.py` keep `TRADING_DAY`. The path must start at the quoted mid and never rise with the stock unchanged, at any expiry.
- **A reading of zero is a reading.** When the options price no extra move for a report, the exit plan shows no step. Past reports size the step only when the options give no reading at all, so the plan never contradicts the earnings section beside it.
- **Skip-earnings fails closed.** With `avoid_earnings` on, a stock whose report date is unknown is left out, an estimated date is given `scanner.ESTIMATE_MARGIN` of room, and discovery does not spend a slot on a stock whose every contract would be discarded (nor give it the usual bonus for reporting soon). Each case adds a warning saying which stocks were left out and why.
- **`earnings_unknown` means no date at all.** A date from the calendar is a date, even when the history lookup behind it failed.
- **Symbols are tidied in `Scanner._scan`** (trim, upper-case, `BRK-B` to `BRK.B`, de-duplicate), so every way in behaves the same.

These came out of the first run against live data (2026-11-24). Each has a test built from a captured response (`tests/fixtures/alpaca_live.json`).

- **A quote from an earlier day is not a quote.** Alpaca's snapshot holds the last quote it saw for a contract. When a special dividend or a split changes a stock's strikes, the contracts that stopped existing go on answering with their final quote, a day old or a year old, and they are missing from the active contract list. `AlpacaData.option_chain` leaves out any quote from an earlier day than the newest quote in its chain (`alpaca._session_day`) and adds a note saying how many. The newest quote sets the day, never the clock, so a weekend scan keeps Friday's quotes; a quote stamped before the 9:30 open does not move the day on.
- **A chain nobody has quoted for days is left out whole.** The rule above compares quotes with each other, so it cannot see a chain whose quotes are all equally old (a halted or delisted stock, whose own last trade is just as old). Only here does the clock decide: if the newest quote is more than `alpaca.MAX_QUOTE_AGE_DAYS` (four, room for a three-day weekend) before `AlpacaData._now()`, none is used and a note says so. Tests that build a chain pin that clock.
- **Volume is the latest session's.** A snapshot's daily bar is from the last day the contract traded, which is often not today. Volume from an earlier day's bar is reported as 0.
- **A stock with nothing to price costs nothing more.** `Scanner._analyze` returns as soon as no quote in the chain can be priced, before the open-interest and earnings lookups. The day's movers include warrants and tiny companies with no options, and an earnings lookup for one can spend an Alpha Vantage request. Such a stock is named in the "no two-sided option quotes" note and in no note about ratings.

These belong to the news layer (phase 2, started 2026-11-24). Each has a test in `tests/test_news.py` or `tests/test_scanner.py`.

- **News is beside the score and the rating, never in them.** An event type is a keyword match, not a judgment: there is no sentiment, and nothing here may feed `scoring.score` or `risk.assess`.
- **News costs nothing for a stock nobody will open, and never sinks a scan.** It is fetched after `scoring.rank`, only for the underlyings of ranked contracts. `_add_news` catches everything per stock, and failures become one warning naming the stocks. It runs before `market.notes` is drained, because loading headlines can add a note.
- **An event sits on the first session whose close reflects it.** News at or after 4 p.m. New York time, or on a day with no session, belongs to the next one. This is `earnings.window`, shared with earnings reactions, so the two can never disagree. Several items of one type on one session are one event, and an event whose session has not closed yet is not counted.
- **The 4 p.m. cutoff stays, though the feed's stamps are batch times.** Decided 2026-11-25, on the review's advice and the saved headlines. The first batch after the close is stamped about 4:31 p.m. and mixes two kinds of story that cannot be told apart: one from 3:45, and an announcement at 4:05. With the cutoff at 4 p.m. the first is measured a session late, which misses the start of the reaction but measures only what came after the news. A cutoff moved past that batch would put the second on the session before it, and measure a move that was over before the news existed. That is the worse mistake, and the batch does hold real after-close announcements (see the measurements below). Do not move the cutoff to make up for the stamps. Only a source that gives the time a story came out would settle it.
- **Earnings days are left out of a study on both sides**: out of the events (the move belongs to the report) and out of the usual day they are compared with. A five-session span with a report in it is left out the same way, from an event's "next 5" and from the usual five sessions, or an event three sessions before a report is credited with the report's jump. The `earnings` type itself gets no study, since the earnings section covers it.
- **The usual day is every session in the stretch, not the days without the event.** For a company in the news most days the complement is a handful of odd days (seen live: NVDA had "agreement" news on 114 of 145 sessions, and the other 31 averaged 3.4% against 2.3% overall). The stretch runs from the first event, over at least `events.BASELINE_SESSIONS`.
- **Below `events.MIN_EVENTS` a study says "too few" instead of showing averages.** Every surface checks this.
- **The company being bought is told from the buyer by name.** The feed tags the buyer, its bankers and the target with the same headline. `events.aliases` gives the ticker and the SEC's company name without its legal ending, and `"to acquire <name>"` then types the headline `takeover` for that company only. A ticker alias matches in capitals only (COST is not "cost"), and a one- or two-letter ticker is not used.
- **Buying something of a company is not buying the company.** The name has to come straight after the buying phrase, and the headline then has to end or turn to the terms (`events._THEN`: a comma, "for", "in", "at" and the like). The first version had no such check, and 7 of the 10 real headlines it flagged were purchases of products or units ("to Acquire NVIDIA GPU Servers", "Acquires Pfizer Brands", "to Purchase Boeing Jets"). A list of words to reject cannot work, because a product name can be anything ("NVIDIA Vera Rubin Systems"). Shares and goods are bought with "to buy", "buys", "to purchase", "purchase of" and "deal for" too, so after those the price or the word "deal" has to follow the name (`events._PRICED`). `events._spelled` settles how much of the name a headline has to give: the first word, two when the first is common ("General Motors", "Home Depot"), and never ending on a joining word ("Bank of America", not "Bank of"). The check stays ahead of the table: a buyout headline often ends "shares jump", which the insider rule would take.
- **A type counts for a company only where the headline puts the company.** The feed's tag says a stock is mentioned, not that the news is its own. With a company name to go by, `events.headline_type` applies four rules, each measured on 4,791 real headlines before it was written:
  - **Some flagged types need the company to open the headline** (`events.IN_FRONT`: guidance, split, financing, distress). In all 33 such headlines where the stock was not the opening name, the news was someone else's ("IREN Secures $3.6 Billion Financing for NVIDIA GPU Acquisition"). Where the company is not in front, the rest of the table decides. Drug news is left out on purpose: "FDA Approves Eli Lilly's Mounjaro" is the usual wording for the company's own news.
  - **A takeover by the table's keywords needs the company on the receiving end** (`events._RECEIVING`), as well as in front. The keywords say a deal is on, not who is being bought: 13 of the 18 takeovers typed live were GameStop bidding for eBay, each marking GameStop as the one being bought and showing the buyout caution. After the rule 3 of the 18 remain, all right, and all by the by-name rule.
  - **A company acting on another is not having the event.** Its name straight before an analyst's verb makes it the writer of the note (`events._WRITES`), and a stake or holding in someone else is a trade in that company's shares (`events._HOLDS`). Both become `another` (`events.ELSEWHERE`, "Another company's news"). These were 183 of JPMorgan's 652 headlines. A banker or investor in someone else's listing or funding round is typed `agreement` by the table, with no name needed.
  - **A headline that names the company nowhere, and whose summary does not either, is `another`.** This needs the feed's one-sentence summary, because a headline alone often has only a product ("Health Canada Approves Mounjaro"): going by the headline was right 60 times in 168, and with the summary 60 times in 76. With no summary on hand nothing is concluded. That measure was on 18 stocks and did not hold on a wider record: see the next two points.
- **With only a ticker to go by, none of those rules runs** (`events._named` returns None). Headlines rarely give the ticker, so every one would look like someone else's.
- **Naming is looser for these rules than for a takeover, but not loose.** `events._named` takes a name with its dots and spaces moved ("J.P. Morgan", "JPMorganChase"), a later word of it alone ("Lilly", "Chase") unless the word is a plain one (`events._PLAIN_WORDS`), and a telling word after a common one ("Bradesco" for Bank Bradesco). Accents are taken off both sides (`events._fold`). The by-name takeover rule keeps the strict spelling (`events._spelled`), since there a wrong match raises a caution.
- **No word merely built on the name stands for it.** That was tried in #18 ("SpaceX" for "space", "Citi" for "citigroup") and taken out after a third review: it made "Metacon" Meta (11 of 12 of that company's headlines came back as Meta's), "Intelligence" Intel, "Gold" Goldman and "Bank" the former BankAmerica. The idea behind it, that looser naming is the safe side, holds only for whether a headline names the company at all. At the front of a headline a wrong match is not harmless: it turns on every rule that asks whether the company opens the headline, so "Bank of England Cuts 2026 Growth Forecast" was Bank of America's guidance. A brand goes in `data/aliases.txt` instead.
- **A company also goes by names that no rule can work out, and those are data.** Names it had before come from the SEC with its filings (`EdgarEarnings.former_names`, noted whenever a filing index is read, at no extra request), and brands come from `data/aliases.txt` (`Settings.aliases`, read for each scan so an edit counts without a restart). `Scanner._called` hands them over apart from the company's own names, as `also` (`events.also_called`). Measured on the wider cache (15,732 headlines, 108 stocks): the never-names-it rule set aside 1,039 headlines and 585 of them were the company's own, under a brand (SpaceX 332, Citi 151, Nubank 63), a former name (La Rosa Holdings, K Wave Media) or an accent (Solésence). With those known it sets aside about 500, nearly all another company with the same ticker in London (Reckitt under RKT, Anglo American under AAL, Pharos Energy under PHAR, Costain under COST, Arecor under AREC, Selvita under SLV).
- **Other names are never given to the by-name takeover rule, and are given whole.** A brand is often one unit of the company: "to Acquire Citibank" or "to Acquire WhatsApp" read as a takeover of Citigroup or Meta put the buyout caution on the wrong company. And a former name is said in full ("Complete Solaria", the name SunPower had), so one of two words or more needs its first two: "Complete Energy ..." is somebody else.
- **A former name counts only while it was still in use within the price history** (`former_names(symbol, since)`, with `since` set `HISTORY_DAYS` back). The SEC keeps every name a registrant ever had, each with the day it was last used, and an old one may be someone else's today: Citigroup was Travelers Group until 1998, and Loop Industries was First American Group until 2015. A record kept before the dates were stored gives no names.
- **A slash inside a registered name is part of it** (`events._plain_name`). Only the tag the SEC adds at the end is taken off (" /NEW", "/DE/", "/ FA"). Cutting at the first slash turned "PRICE/COSTCO INC" into the alias "price" for Costco and left "M/I HOMES" with no name.
- **The scan says when most of a stock's headlines never name it** (`scanner.UNNAMED_SHARE`, in `UnderlyingContext.naming_note`). No rule can tell a look-alike ticker from an unlisted brand, so the person is told and can add the name to `data/aliases.txt`. It is kept apart from `news_note`, which is about a source that failed or cannot answer: the remark about names is for the person at the screen, is not copied into a failure warning, and is not sent to the AI brief, which is given neither the set-aside headlines nor a count of them.
- **Someone else after the name is looked for once the whole name is matched** (`events._SOMEONE_ELSE`, in `headline_type`), never inside the name's own pattern. Inside it, a miss sent the matcher back to a shorter reading of the name ("Costco" out of "Costco Wholesale"), the next word was then the company's own, and the check passed. So "Costco Wholesale Supplier Foxconn Cuts Outlook" was Costco's guidance, and the same for every company with a name of two words or more.
- **A name needs three letters in all, however many words that takes** (`events._needed`). "GE" is not enough for GE Vernova and "W W" is not enough for W.W. Grainger. Stopping at the first word left 279 of the 10,400 companies the SEC lists with no usable name, which switched every whose-news rule off for them.
- **Another company's news counts towards nothing and is still there to read.** `events.context` gives it none of the ten places, keeps it out of every study (`NOT_STUDIED`), and hands the newest `MAX_ELSEWHERE` back apart (`UnderlyingContext.news_elsewhere`). The count stays in `recent_events` under `another`. The dashboard shows them in a folded section so the rule can be checked. The command line and the AI brief leave them out, items and count.
- **The feed's summary is kept, not shown, and not sent to the model.** `NewsItem.summary` is read only to tell whose news a headline is. Headline records are stored as `news_headlines2_<symbol>`; a record from before summaries were kept (`news_headlines_<symbol>`) is left where it is and the stock's headlines are asked for afresh.
- **A by-name takeover is not a domain, a list, or a sale of assets.** In `events._THEN` a full stop counts only when no letter follows it ("Acquires SHOP.COM Domain Name"), and a list of names before the thing bought is turned away ("Acquires Apple, Microsoft and NVIDIA Shares"). "Explores Sale" is a takeover only when it is not a sale of something else (`events._EXPLORES_SALE`), and a mini-tender is typed `disclosure` ahead of the takeover rule. Three of the twelve takeovers in the cache were these.
- **What a company says about the quarters ahead is guidance, even when it names a quarter.** The results rule comes first in the table and results are neither pointed out nor studied, so it must not take "Fourth Quarter 2026 Revenue Guidance" (`events._AHEAD`), preliminary results, or an outlook that falls short (the early `guidance` rule). Results with guidance alongside stay `earnings`.
- **Distress and a change of control come ahead of results in `FILING_ITEMS`.** A delisting notice or a restatement is often filed with the quarter's results (ten such filings in the cache), and typed as results it lost its chip. A company buying out of someone else's bankruptcy is not in distress (`events._ACQUIRING`).
- **A flagged type needs more than one loose word.** "Default", "prices" and "positive data" each typed an everyday headline as distress, an offering or a drug trial (the default search engine, a headset's price, a chip's benchmark). Each now needs its context: what is owed, a security, a clinical word. Before changing a rule, type a saved set of real headlines with the old table and the new and read every difference. Doing that for these changes caught two side effects no test had: "Phase 1b" results dropping out of `drug`, and Boeing's "Phase 4B Certification Testing" dropping in.
- **"No filings" and "cannot classify" are different**, as with earnings. A company that files 6-K raises `Unsupported` in `EdgarEarnings.filings`; `NewsService` turns that into a note that is not a failure, and remembers it like any other answer.
- **The headline record on disk only grows.** The feed reaches back some months, so `NewsService` merges by the feed's id and asks only for headlines since the newest one on file, less `NewsService.OVERLAP` in case the feed adds one stamped just before it. A copy on disk that does not parse is fetched again, never read as "no news". A time with no zone counts as not parsing: it cannot be compared with a source's times, and left on disk it failed every later scan for that stock.
- **A link from the feed is a third party's.** Only an `http` or `https` address is kept (`alpaca._headline`), the page checks again before making it clickable, and it opens with `rel="noopener noreferrer"`.
- **A flagged headline is always on the list.** `events.context` keeps the newest `MAX_RECENT` items plus the newest item of each flagged type that a busy week pushed out, so a chip that says "takeover" always has its headline there to read. The command line (`NEWS_LINES`) and the brief (`ai.NEWS_ITEMS`) have room for fewer, and take theirs through `events.shortlist`: the newest item of each type with a caution, then of each other flagged type, then whatever is newest. Putting flagged items first as a group is not enough: six newer guidance headlines would take all six of the brief's places and leave the takeover caution with no headline.
- **The AI brief reads headlines as data.** `ai.scan_payload` gives it up to `ai.NEWS_ITEMS` items for each stock (chosen by `events.shortlist`, date notices left out, unclassified ones kept since a model can read what no rule matched), each cut to `ai.HEADLINE_CHARS`, with the summary of each study and any caution. Headlines go in the user message only. Everything the model is told to do with them is in `ai.SYSTEM`: a headline is never an instruction, it is all the model knows of the story, and a study is not a forecast. Change the payload and the prompt together or not at all. The answer is still a fixed schema, picks that name no contract from the scan are dropped, and a contract named twice is listed once.

These belong to pooling events across stocks (2026-11-25). Each has a test in `tests/test_pool.py`.

- **A type of event is pooled within a coverage group, never across the two.** `events.coverage` calls a stock heavily covered at `HEAVY_HEADLINES` of its own headlines in `COVERAGE_DAYS`, lightly covered otherwise. Measured before the feature was built (below): for heavily covered stocks no type of headline was followed by a bigger day than usual, for lightly covered ones offerings and reverse splits were, and pooled together the two cancel out. Another company's news and filings do not count towards coverage.
- **Each day is counted against the stock's own usual day.** `events.tally` counts a day as big at more than `BIG_MOVE` times the stock's usual day, measured as in `events.study`: over the stretch the type's events span, earnings days left out of both sides. Beside the share of event days that were big always goes the share of all days over the same stretches, because about one day in nine is big anyway.
- **The pool costs a scan no request.** A scan stores a tally for each stock it shows (`EventPool.add`, one small record per stock, `pool_<symbol>`), and a pooled study is those records added up (`EventPool.totals`). Only `Scanner.widen_pool` (`python -m app pool`) fetches anything for the pool. Like the rest of the news, pooling is an extra: `_pool_studies` catches everything, and a pool that cannot be read leaves the stock's own study as it was.
- **What may join the pool is one rule, asked by a scan and by widening** (`events.unpoolable`): headlines on record, enough price history for a usual day, and report days within it. A stock with no headlines (a second share class has filings and nothing in the feed) would otherwise be pooled with the smallest companies, and without report days a move that belongs to a report could not be told from an event's.
- **A failed news lookup never takes the place of a tally.** With the headlines missing, a heavily covered stock looks lightly covered, and its filings-only tally would overwrite the full one for months. A scan leaves the pool record alone when a lookup failed, and `widen_pool` passes the stock over and says so.
- **Report days for a stock nobody is scanning never cost a rate-limited request, and are kept nowhere** (`EarningsService.reports`). What is on file answers if a scan would still trust it, "no reports" included; otherwise the first source alone is asked, unless it is marked `rate_limited` (Alpha Vantage). Its answer is not stored, so it cannot stand in later for the fuller history a scan would get. Stale reports are not used: they lack the newest report days, and a move on one of those would be counted as an event's.
- **Below `events.MIN_POOLED` events a pooled study says "too few".** Every surface checks this.
- **A tally older than `EventPool.KEEP` is left out, and a stock's new tally takes the place of its old one.** A record that does not read as a tally is passed over.
- **The demo's pool lives in memory** (`MemoryCache`), never on disk, and starts with every demo stock in it.
- **The AI brief is not given pooled studies.** They would need the prompt to say what they are, and the payload and the prompt change together or not at all.

These belong to the positions page (phase 3, started 2026-11-25). Each has a test in `tests/test_positions.py`.

- **The positions file is handled the opposite way to the cache.** It is the person's own and cannot be fetched again. A file that does not read is an error (`positions.StoreError`), never "no positions": read as empty, it would be written over by the next entry. An entry that does not read stays in the file as it was written and is counted in a warning. A write that fails is an error. Entries are written back as they were read, so anything a person adds to one by hand survives.
- **Demo positions live in memory** (`positions.open_store`, `PositionStore(None)`), like the demo's pool. Demo data never reaches the disk, and the person's own file is never shown under the demo badge.
- **A position is always listed.** `Scanner.review` catches each source on its own (stock prices, option quotes, price history, one stock's lookups) and turns a failure into a warning, and `holdings.assess` works with every input missing. An expired position gets one check and costs no request, and is not set beside its stock's news even when another position on the stock is open. With no keys at all the server still lists what is on file.
- **A failure costs a position only what depended on it.** When a stock's earnings dates cannot be looked up, its price, Greeks, path and news stand, and its earnings check says "unknown". The first version dropped the whole stock and told the person it had no price. The strike is set against the stock's price whenever there is one.
- **A check that cannot be made says "unknown" and never passes.** That covers no earnings date, an estimated date just past the expiry, no ask to buy back at, and no stock price. It is skip-earnings failing closed again, and an estimated date gets `scanner.ESTIMATE_MARGIN` of room here too.
- **A result is priced where the position would be closed**: the bid for a holder, the ask to buy back (`holdings.result`), across every contract. It needs only the side that closing uses, so it survives a quote the scan's math turns away for want of a bid. An option sold that is now nearly worthless often has no bid, and buying it back needs only the ask.
- **A quote that is no price to close at gives no result and settles no target** (`holdings.unusable`). That is a crossed quote, and one that is below exercise value even at its ask, which is out of date against the stock. It is what an earnings night looks like: the stock trades on after the close and the option's quote does not. Read as it stood, a put sold for $2.00 and $20 in the money showed +$150 and "profit target reached". A bid under exercise value with the ask above it is an ordinary deep in-the-money quote and stands, and so does any quote when there is no stock price to hold it against. The row still shows the bid and ask, and its note says why there is no result.
- **Only a seller has a profit target, and only a short option is pointed out for being through its strike.** `exits.PROFIT_TARGET` is a seller's rule and no buyer's rule was made up to match it. In the money is what a holder is waiting for, so for a holder it is said and not flagged. The time stop is counted for both.
- **A review pulls no chain.** Held contracts are asked for by name, a hundred to a request, whatever their stocks. The two rules about a quote's age apply as they do to a chain, with the newest quote among the contracts asked for setting the day.
- **A held contract's quote from an earlier day comes back marked, not missing** (`OptionQuote.outdated`). Its prices are left out, since it is not a quote, and its time is handed on. A chain says how many it dropped. A position says "last quoted on Nov 20", where "no quote found, check its strike" would send the person after a strike that is right.
- **Without the chain there is no reading of what the options price for a report.** `ctx.implied_move` and `ctx.atm_iv` are None in a review, so the step across earnings in a held contract's plan is sized from past reports, and the plan carries a note saying so. This is the case `exits._place_report` already had for "no reading at all", and nothing beside it on the page shows a priced-in move to contradict.
- **The path for a held contract is the scan's path with another entry price** (`exits.build(entry=)`). It still starts at the quoted mid. Only what a result is measured against changes. A checkpoint's result is for one contract, and `Holding.pnl` is for all of them.
- **The strike is measured one way**: `strike / stock - 1`, as `ExitPlan.strike_distance_pct` has it. The first version of the check used `stock / strike - 1`, and the page showed 4.3% in the check and 4.1% in the plan for the same gap.
- **A rule that is reached is a fact about the position, not an instruction.** No surface says to close, roll or hold.
- **What the person paid and how many they hold never leave the machine.** A review sends tickers and contract symbols and nothing else, and the AI brief is not given positions.
- **The routes that change the file take JSON only.** A form on another site can post text without the browser asking, but not JSON, and FastAPI reads a body as JSON only when it is sent as JSON. The page asks once more before removing an entry, since one cannot be brought back.

These belong to paper trading (phase 4, started 2026-11-26). Each has a test in `tests/test_paper.py`.

- **One module sends an order, and it knows one host.** `app/broker.py` is the only file with an order endpoint in it, and `PAPER_URL` is the only address it has. The address is not a setting and `AlpacaPaper` takes none. With `ALPACA_PAPER` off there is no broker at all (`paper.build_desk`, `paper.LIVE_KEYS`): the app scans, reads the journal, and sends nothing. A test reads the source for both. `providers/` stays read-only, as its docstring says.
- **Every order is the person's, and is sent once.** An order is written out first as a `Ticket` (`PaperDesk.write_open`, `write_close`), which sends nothing and writes nothing. `PaperDesk.send` takes a ticket's id and nothing else, uses the ticket up, and turns away one older than `paper.TICKET_MINUTES`. So what reaches the broker is what was shown, and a second click or a replayed request sends nothing. `POST /api/paper/orders` is the one route that sends, and on the command line nothing is sent without `--send`.
- **Looking never sends or cancels.** `PaperDesk.review`, a scan, and a rule being reached send no order. A test runs reviews over a position whose profit target is reached and counts the orders.
- **The two routes that write an order out or send one take JSON only**, as the positions routes do, and the server makes up neither a quantity nor a price: both come from what the person was shown.
- **An order is a day limit order for whole contracts of one option, priced in whole cents** (`broker.check`, and `PaperDesk.sized` before it). There is no market order, no order that outlives the session, no second leg and no stock order.
- **Sending is never retried.** A request that timed out may have arrived, and a second one would be a second order. `BrokerError.refused` says which it was: the account answered and said no, or nobody can tell. A 5xx is "nobody can tell". Reading is retried like any other lookup.
- **The journal is written before the order leaves**, so an order is never out there with no record of it. An order the account turns down outright is taken back out of the journal: nothing happened. One whose answer was lost stays as ordered, and the next review asks the account for it by the id this app gave it (`paper.open_id`, `Broker.order`).
- **Only the account saying it never had an order makes it one that never arrived, and only for an order it never confirmed.** An order that is missing from the list is asked after by name (`Broker.order`), since a long list can be cut short. One the account confirmed is waited for even if it then says it has none by that name. An order that cannot be asked after is waited for. Neither is written off (`paper.reconcile`, `find`).
- **An order still working changes nothing in the journal, however much of it has filled.** A trade is open once its order has ended, at the account's average fill and for as many contracts as filled, and a closing order becomes an exit the same way. While a closing order is working, contracts missing from the account are taken to be that order's, and nothing else is concluded about them.
- **Opening goes through a scan.** A paper trade is opened from a contract in a `ScanResult` (the page's scan in memory, or a one-stock scan the command line runs), so the journal always has what the scan showed. `signals.snapshot` copies it as plain values, and the copy is never recomputed: a later change to a weight does not rewrite what was shown.
- **The rules reached at the close are read when the closing order is sent** (`PaperDesk._rules_now`), and go with the order to the exit. When they cannot be read they are None, "not on record", and never guessed. That includes a review that answers "unknown" for a rule a closed trade is sorted by (`journal.ENDED_BY`): see the review's points below. The order is sent either way: it is the person's.
- **The journal file is handled like the positions file**, by the same class (`store.ListFile`). A file that does not read is an error, an entry that does not read stays as written and is counted, an entry repeating an id is never changed with the first, and anything added to an entry by hand survives a save. The demo's journal and account live in memory.
- **The result on file is never trusted over the exits.** `journal.settle` works out the state, the result and `stands` from the exits every time an entry is read or written. A result is an amount in cents (`round(..., 2)`): 100 times (1.03 less 0.52) is 51.00000000000001 in floating point.
- **Contracts the account no longer holds are accounted for in a fixed order** (`paper._unheld`): by a filled order this app did not send (the trade was closed at Alpaca), else at expiry, else as "unknown" with no price. An order from before the trade opened, and one already counted, are not used. With two trades on one contract the older is closed first.
- **Nothing is concluded when the account's positions could not be read.** `reconcile` is handed None for them and skips that pass. Read as "holds nothing", every open trade would be written off.
- **A trade held to expiry is settled at what exercising it paid at that day's close**, which is how a scan scores a contract. Until that day's bar is final the trade waits as it is. The shares an exercise or assignment leaves behind are not followed, and the entry's note says so.
- **An exit with no price gives no result, and the trade is counted nowhere** (`signals.counted`). Nothing is made up for it.
- **Paper and real are never mixed.** The desk does not read or write the positions file. What the paper account holds is reviewed through the same `Scanner.review` and `holdings.assess`, as `Position`s built from the account (`PaperDesk._position`). A share class goes by the stock's own spelling from the journal (BRK.B), since an option's symbol has no dot.
- **The summary of which signals worked keeps four promises** (`analysis/signals.py`). Bought and sold options are never counted together. Below `signals.MIN_TRADES` a row says "too few" on every surface. Each row sits beside the row for every closed trade of its lens. And nothing in it feeds `scoring.score` or `risk.assess`: the journal is beside the score and the rating, never in them.
- **A trade's standing is worded once, in Python** (`Trade.stands`, from `journal._stands`), as a check on a position is.
- **A call sold to open is said to need the shares before it is sent**, and the demo's account turns it down as Alpaca does.
- **What leaves the machine.** A paper order sends its contract, its number of contracts and its limit to Alpaca's paper account. That is the only place a quantity or a price is sent. What the person really holds and paid still never leaves, and the AI brief is given neither the journal nor the paper account.
- **On the page, an order is sent from one place** (`orderBox`). Send and the button beside it are off from the first click, a failed send leaves Send off because the ticket is used up, and an answer about the paper account that is not the newest load's is dropped (`paperLoads`).

Asked only the first time, two orders for the two sides of one contract could both be written out before either was sent (two tabs, or the command line while a ticket waits its ten minutes), and both were sent. At sending the answer is 409 and the ticket is used up, as for a closing order whose trade has changed. The demo's account turns such an order down as well, in its own words: what Alpaca says to one has not been seen, so nothing is passed off as Alpaca's.
- **The demo's clock is set once and then only runs forward** (`paper._demo_clock`). It starts on the demo's day at the time it is in New York, and adds the time that has really passed. Read afresh each time as "the demo's day at the time on the wall", it went back a day at midnight in New York: an order written out at 11:55 p.m. was still taken twenty minutes later, a trade closed after midnight was closed before it opened, and the clock went back an hour when the clocks did. A demo left running past midnight is therefore a day ahead of its market's day, which stays where it started.
- **A fill has a position's bounds at both ends** (`paper._fill`). Only the floor was checked. A fill above `positions.MAX_PRICE` opened the trade, the journal wrote it down, and then could not read its own entry back.
- **An order that filled with no price is never said to be waiting to fill, or working** (`journal.unpriced`, `journal.NO_PRICE`). It is neither. The remark `reconcile` puts on the trade is the only record of it, so everything worded about the trade asks `unpriced` first: where it stands (`journal._stands`: "ordered, waiting for the price it filled at", "open, waiting for the price its closing order filled at"), what is said as the order is sent (`_sent` on the command line, `sentText` on the page), and the page's "Close it", which said the order was in the list of orders, where it is not. The page tells the remark by how Python begins it (`status.paper.no_price`), and holds no copy of the words. The constant lives in `journal.py` because `_stands` needs it and `paper.py` imports the journal, not the other way round.
- **On the page, cancelling an order clears the line about the last order sent** (`say("")` in `renderOrders`). "Sent. The closing order is working." stayed above the lists after that very order had been cancelled.
- **A cancel the account turns down is read afresh** (404 or 422, in `renderOrders`). The order has filled or ended, so the list the button was pressed in is out of date. The reason goes on the line above the lists, since reading the account afresh redraws the row. Any other failure is nobody-can-tell: the reason stays beside the button, which can be tried again, and nothing is reloaded.

## What live data looks like

Measured on 2026-11-24 after the close, with paper keys on the free plan. Use these when judging whether a result is a bug.

- **Greeks and implied volatility arrive for most contracts, not all.** The indicative feed sent them for 80% to 97% of a chain. It sends none for a contract with no bid, and none for many deep in-the-money ones. `contracts.analyze_contract` then solves its own, in the same units (theta per day, vega per volatility point).
- **Open interest lags and has gaps.** It comes from the paper trading host's contract list, as text, and was dated 2026-11-20, two trading days before the scan. A contract listed since then has none: 13% to 41% of a chain. A known zero never appears. `scoring._liquidity` scores a contract with no figure on its spread alone.
- **Dropped quotes are far from the money.** After the close, 1% to 12% of a chain was dropped: no bid (far out of the money), a midpoint below exercise value (deep in the money: delta 0.76 or more, above 0.9 for nearly all, where the bid sits well under exercise value and the ask just above it), and a handful with no volatility that solves. None was a contract either lens ranks.
- **After the close the stock keeps trading and the option quotes do not.** The scan price is the last trade on IEX, which after 4 p.m. is an after-hours trade, while every option quote is from the close. ORCL was 1.0% below its close and 44 of its puts had their whole quote under exercise value. On an earnings night that gap is the whole move, and out-of-the-money quotes are just as out of date with no check to catch them. Alpaca's own implied volatility and Greeks move with it: 45 minutes apart, with the option quote unchanged and NVDA 1.2% lower after hours, a put's implied volatility went from 58.8% to 56.5% and a call's from 64.5% to 67.0%. So when a stock falls after the close its puts look cheaper and its calls dearer than they were. Not handled yet: the scan neither uses the close nor says the stock has moved since. Two facts for whoever fixes it: the IEX snapshot's `dailyBar.c` stayed at the 4 p.m. price while `latestTrade` moved on (checked until 5:20 p.m.), and option quotes did not all stop at 4:00 (SPY's ran to 4:15, and some AAPL and NVDA quotes were stamped as late as 4:14), so no single stock price fits a whole chain. Switching to the close is not enough on its own, because Alpaca's implied volatility and Greeks would still belong to the later price.
- **Consolidated price history is allowed** on the free plan when the request ends at least 15 minutes ago, which `daily_bars` already does. The IEX fallback did not trigger.
- **The screeners are allowed** on the free plan. The movers list includes warrants and tiny companies with no options, so a discovery scan loses a few of its 20 slots to them. Each costs one chain request and is named in one note.
- **The stock price is only as fresh as the last IEX trade.** A stock that rarely trades there can be weeks out of date (a warrant on the movers list last traded five weeks earlier). An IEX daily close differs a little from the official one, and `change_pct` is not adjusted for a dividend or a split.
- **Alpha Vantage's calendar is short and slow.** It listed 669 companies for three months and had no date yet for the large companies' January reports, so most upcoming dates are still estimates. One history request in ten hung for the full 30-second timeout. A first discovery scan took 48 seconds, 38 of them waiting on Alpha Vantage; with earnings history cached it takes about 3.
- **Rate limits were never close.** Each Alpaca host allows 200 requests a minute. A discovery scan made 68 requests in all.
- **A buyout breaks the rating.** Once a cash takeover is agreed the stock sits at the deal price and its options price almost no movement (INSM: 6% implied against a volatile history). Every option then looks cheap next to history and the rating says "favorable". The rating itself still does not detect this. The news layer flags it when a headline names the stock as the company being bought ("Sanofi to Acquire Insmed" put a takeover chip and a caution on INSM), which is no help for a deal the feed words another way.

Paper trading, from Alpaca's documentation as read on 2026-11-26. What was then seen of the paper account, on 2026-11-27, follows this list.

- **An option order** goes to `POST /v2/orders` with `symbol` (the OCC symbol), `qty` as text, `side`, `type`, `time_in_force`, `limit_price` as text, `position_intent` (`buy_to_open`, `sell_to_open`, `buy_to_close`, `sell_to_close`) and `client_order_id` (128 characters at most). The quantity must be whole, extended hours are refused, and a market order is taken only during market hours. The app sends `limit` and `day` only.
- **The pages disagree with each other in places.** One lists market and limit orders and `day` only, another adds stop orders and `gtc`. One says do-not-exercise goes through the API, another through support. One has orders that open a position stopping at 3:30 p.m. on expiry day, another has a sell-out "within 1 hour before expiry".
- **The account answers with numbers as text** (`"qty": "2"`, `"filled_avg_price": "2.05"`), and `filled_avg_price` can be null.
- **An order that will not change again** is `filled`, `canceled`, `expired` or `rejected`. `broker.DONE` adds `replaced`. Everything else is treated as working, `done_for_day` included.
- **A position** has `asset_class` `us_option`, `side` `long` or `short`, and `avg_entry_price` per share (inferred from the example: 2 contracts at 6.05 have a `cost_basis` of 1210). Whether `qty` is negative for a short position is not stated, so `broker.py` reads the side and takes a negative count as short too.
- **Options levels.** 1: covered calls and cash-secured puts. 2: also buying calls and puts. 3: also spreads. A paper account has options on by default, at a level the pages do not give: the person's answered level 3 on 2026-11-27, with $100,000 of options buying power. Refusals come with the reason in words ("insufficient options buying power for cash-secured put (required: 20310, available: 9395)", "insufficient underlying qty available for covered call (required: 100, available: 0)"), and the app shows them as they are.
- **Paper fills.** An order fills only when it becomes marketable, against real-time quotes, whatever its size. One time in ten a fill is partial, for a random amount. The page about paper trading does not mention options at all.
- **At expiry** an option in the money by a cent or more is exercised or assigned, and a long one the account cannot afford to exercise is sold first. Exercise, assignment and expiry are recorded as account activities (`OPEXC`, `OPASN`, `OPEXP`), which a paper account shows only the next day. The app does not read them.
- **The reference pages for listing orders, getting one, and cancelling one could not be opened** (404 on 2026-11-26). `GET /v2/orders` with `status`, `limit`, `after` and `direction`, `GET /v2/orders:by_client_order_id`, and `DELETE /v2/orders/{id}` answering 204, or 422 when it is too late, are written from memory of the API.
- **The outside review of 2026-11-26 says it checked those three against Alpaca's documentation and found them as written**: `status` (`open`, `closed`, `all`), `limit` (500 at most), `after` (a time, exclusive) and `direction` on the list, a 200 or a 404 by client order id, and 204 or 422 on cancelling. It also reports that a position's `qty` is positive on REST with the side in `side`, and that the account has `options_trading_level` and `options_buying_power`. That was not checked again here. Of it, the first read of the account (2026-11-27) bore out the two account fields and that the list of orders takes `status`, `limit`, `after` and `direction`. The first orders, later that day, bore out the 200 and the 404 by client order id and a long position's positive `qty`. A cancel sent from the page took that day, but the status Alpaca answered it with was not captured.
- **Two things the same review says to expect on the first run.** A limit price has to be on the contract's tick (a nickel for some contracts, by price), and Alpaca answers 422 for one that is not, which the app shows as it is and takes back out of the journal. And an order filled in part can be `done_for_day` after the session before it becomes `expired` or `canceled`: the app treats that as still working, which is the safe reading. Neither came up on the first orders: all six were in whole cents on contracts that take them, and none filled in part.

Paper trading, seen on 2026-11-27. The person sent their first orders from the live dashboard between 11:47 and 11:55 a.m. New York time: six orders to buy one contract to open. Four filled and two were cancelled. The account's rows were read afterwards with GET requests only, at 11:53 a.m., at 1:25 p.m., after the half day's close, and at 5:46 p.m.

- **An order at the ask a scan showed does not always fill at once.** Five were priced at the ask of a scan 14 seconds to two and a half minutes old. One filled in a seventh of a second, a cent under its limit. Two filled after 11 and 21 seconds, and one after 3 minutes 49 seconds. ## Working agreement

- Branch off `main` for each change. Commit, push, open a pull request, merge, and delete the branch only when asked for that step. Merge with a merge commit.
- GitHub deletes a pull request's branch on its side when it merges (a repository setting, on since 2026-11-25). The cleanup step is then the local half: switch to `main`, pull, delete the local branch, prune.
- Auto-merge is allowed on the repository, and with the rule on `main` it has the two required checks to wait for. Turn it on only when asked, and with the merge-commit method: the default is squash.
- Auto-merge has to be turned on while a required check is still running. The two checks finish in about a minute, and once they have passed GitHub refuses it ("Pull request is in clean status"). That happened on three pull requests (#15, #17, #18), each time because it was asked for after the pull request was already open. It first took on #19 (2026-11-26), asked for straight after the pull request opened, and GitHub merged it with a merge commit when the second check passed. So if auto-merge is wanted, ask for it with the pull request, and turn it on in the same step that opens it. If it is refused because the checks have already passed, merging directly with a merge commit gives the same result.
- Do not place trades, and do not say what to trade. Explanations of the numbers are welcome.
- That covers paper orders. Sending one is the person's step: the Send button on the page, or `--send`. Decided 2026-11-26, when phase 4 was started: asked whether an order should ever be sent without the person pressing a button for that one order, the answer was no. So try the order path on the demo account, on the tests' stand-in (`Account` in `tests/test_paper.py`), or by writing an order out without sending it. Ask before sending one to the real paper account, even to check a fix, and say which order.
- Reading the paper account (`python -m app paper`, the Paper view) sends nothing, but it does write: it brings the person's journal up to date. That is what it is for, and it is fine to run when the person asks to see the account.
- There is no screenshot or OCR path, by decision. Do not add one.

## News layer: what is left (not started)

In so far: typed headlines and filings, a per-stock study of what followed, the news in the AI brief, rules for whose news a headline is, and types pooled across stocks covered about as much. Ask before building any of these.

- **What pooling does not do.** It compares the day itself, not the five sessions after it. Stocks are grouped by coverage alone, not by size or by industry. The AI brief does not read it. In the lightly covered group three years of 8-K filings outnumber seven months of headlines, so its figures say more about filings than about headlines. And a pool widened from the day's movers leans towards small, volatile companies.
- **Left from the second outside review, by decision.** The by-name takeover rule still wants the strict spelling, so "to Acquire Disney" is missed where the name on file is Walt Disney. An analyst's preview that names a quarter ("Oppenheimer Projects CoreWeave Q2 Revenue ...") is still typed `earnings`. `AlpacaData.daily_bars` still takes the end of its range from the wall clock. The public page in `docs/` does not mention whose-news or pooling.
- **What the whose-news rules do not settle.** A partner's or a customer's press release that name-drops the stock still counts as the stock's ("Dell Introduces Server Featuring NVIDIA ...", "... Launches at Costco"): no rule tells that from a small company's landmark deal. A company's own strategic stake is set aside with a bank's routine holdings ("GameStop Increases Economic Stake in eBay", "Pfizer Divests Stake in ViiV Healthcare"). A different company with the same name is not caught ("Oracle Commodity Holding" under ORCL). The guidance keywords cannot tell a bank's forecast for oil from its own outlook. And a takeover target is missed when the headline opens with its name but words the deal in a way `_RECEIVING` does not list.
- **Classify with a model instead of keywords.** It would fix much of the 28% that fit no rule, at a cost per headline and with rules nobody can read. Keyword rules were chosen because the scan's rules are meant to be visible.

## Positions page: what is left (not started)

In so far: a file of entries, a review that sets each one beside today's quotes, the four checks, the path from the entry price, the stock's news, and all of it on the page and the command line. Ask before building any of these.

- **A record of a real position after it is closed.** An entry is removed and nothing of it is kept. The journal (phase 4) records paper trades only, by decision: it is not given the positions file.
- **Editing an entry.** An entry can be added and removed. To change one it is removed and entered again, or the file is edited by hand.
- **Positions with more than one leg.** A spread is two entries, and their rules are not combined: the most a vertical can lose, or a covered call's shares, are not known to the page.
- **The chance of reaching a target before expiry.** It depends on the path. If it is ever shown it needs its own model (first passage or a simulation), never the chance of profit at expiry.
- **Early assignment around an ex-dividend date.** It matters for short options and needs a dividend data source. The pricing assumes no dividends, and the plan's note for a short call says so.
- **What the options price for a held stock's next report.** That takes the chain around the report, which a review does not pull. It could be fetched for one position when the person asks for it.
- **A stock price from after hours.** After 4 p.m. the strike check compares the strike with an after-hours trade while the option's quote is from the close. Where the move puts an option's whole quote under exercise value, the position now shows no result and says the quote is out of date. A smaller move leaves a quote that is just as old and looks fine, and nothing catches that. This is the scan's open problem too (see "What live data looks like").
- **Anything that watches.** A review runs when the view opens or Refresh is pressed. With free delayed quotes a signal is end-of-day quality, so no timer and no alert was built.

## Phase 4: paper trading (started 2026-11-26)

Asked for on 2026-11-26. Three things were decided with the person before anything was built:

- **Every order is the person's.** No order is sent without them pressing a button for that one order. The app may not open a trade from a scan on its own, and may not close one when a rule is reached.
- **Paper trades have their own view**, read from the paper account. `data/positions.json` stays for what is really held, and the two are never mixed.
- **The journal follows paper trades only.** Following every ranked contract with no order, priced at later quotes, was offered and turned down for now. It would give far more data, with no bias from what the person picked.

"What this is" and the working agreement were rewritten on that basis. The wording is a draft until the person has read it.

In so far: the broker, the journal, the desk between them, the Paper view, `python -m app paper`, and the summary of which signals worked. Ask before building any of these:

- **A covered call.** A call sold to open needs 100 shares in the paper account, and the app sends no stock orders. So a paper trade under the sell lens is a cash-secured put, unless the person buys the shares at Alpaca first.
- **Any order but a day limit order for one option.** No market orders, none that lasts past the day, no spreads, no rolling a trade in one step, and no changing an order that is working: it is cancelled and written out again.
- **Closing part of a trade.** A closing order is for everything that is left.
- **Shares after expiry.** An option that expires in the money is exercised or assigned, and the paper account then holds shares or is short them. The journal settles the trade at that day's close and says so. Nothing shows or closes the shares.
- **A position opened at Alpaca itself.** It is listed, and has no journal entry and no way to close it from here.
- **Anything that watches.** A review runs when the view opens or Refresh is pressed, as for positions.
- **The readings the summary sorts by.** `signals.GROUPS` has six, with fixed bands (`SCORE_BANDS`, `POP_BANDS`). Delta, days to expiry, the score's components and the size of the spread are in each entry's `signals` and are not summed up yet.
- **The journal in the AI brief.** It is not given the journal or the paper account.
- **Real positions in the journal.** See "Positions page: what is left".
- **Left from the phase 4 review.** With the list of orders cut short, a trade whose contracts have left the account (closed at Alpaca, or expired) stays open in the journal until the list can be read whole, and it is that trade's own age that keeps the list long. Reading the newest orders first, or asking for one contract's orders by `symbols`, would get past it, and both need parameters nobody has checked. The rules are still read with a price history request and an earnings lookup while a closing order waits to leave, under the desk's lock, and no time limit is put on that: the page says "Sending…" meanwhile. A limit is rounded to a cent and not to the contract's tick. And the page does not guard a journal entry's signals against every shape a hand edit could give them, as `signals.py` now does.
